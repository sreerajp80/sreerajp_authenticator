# Phase 8 (CI) and a setting to block screenshots

**Status:** completed

Implements Phase 8 of `plans/20261029_183929_adopt-updated-guidelines.md` and adds one new setting.

**Security impact:** This plan lets the user turn off screen capture protection on Android.
Protection stays on by default. The CI workflow uses no secrets and read-only permissions.

## What the issue is

1. **No CI.** The repository is on GitHub, and engineering standard §19.1 requires a checks-only
   workflow. `.github/` does not exist yet.
2. **Screenshot blocking cannot be changed.** `lib/main.dart` always turns on `FLAG_SECURE`
   (the Android flag that blocks screenshots). The user wants a setting for this, on by default.

## Plan for the fix

### Part A: CI

Add `.github/workflows/ci.yml`, following §19.1:

- Runs on pull requests and on pushes to `main`.
- `permissions: contents: read`, no secrets, one `ubuntu-latest` runner.
- Flutter pinned to exactly `3.47.6`.
- Steps: checkout, set up Flutter, `flutter pub get`, `dart format --output=none
  --set-exit-if-changed .`, `flutter analyze`, `flutter test`.
- No `build_runner` step (the app has no code generation that uses it).
- No submodule checkout (no test or analysis step reads `docs/guidelines/`).
- No Dependabot, no builds, no signing, no uploads (§19.2, §19.3).

### Part B: Setting

**Behaviour**

- New switch "Block screenshots" on the Security screen, in its own section. It is shown even
  when app lock is off, because it does not depend on app lock.
- Default is on. A missing saved value counts as on, so existing users stay protected.
- Android only. Windows and Linux have no protection to turn on, so the switch is hidden there.
- Turning it off shows a warning dialog first. The warning says that screenshots, screen
  recordings and the recent-apps view can then show codes and secrets. Turning it on needs no
  dialog.
- The change applies at once, with no restart.
- The setting stays on this device. It is **not** added to Wi-Fi sync or backup settings, so
  data from another device can never turn protection off.

**Startup (safe by default)**

`main.dart` still turns protection on first, as it does today. It then reads the saved value and
turns protection off only if the user chose that. If anything fails before that point,
protection stays on.

**Code**

- `lib/utils/screen_protection.dart`: add `setScreenProtection(bool enabled)`, which calls the
  plugin's on or off methods. It does nothing on Windows and Linux.
- `lib/providers/settings_provider.dart`: add the `block_screenshots` key, a getter and
  `setBlockScreenshots(bool)`. It applies the change first and saves it only if that worked.
- `lib/main.dart`: apply the saved choice at startup (kept to a few lines).
- `lib/screens/security_screen.dart`: add the section, the switch and the warning dialog.

**Text**

- New ARB keys in `en`, `ml` and `sa`: section title, switch label, switch description, dialog
  title, dialog body, dialog confirm button.
- Correct text that is no longer true: `helpVault08` says the app "always" turns on the flag.
  Also check `helpVault09`, `helpVault10`, `helpFaq12`, `descFeatures47` and `descFeatures50`,
  and say that this is the default and can be changed in Settings.
- Run `flutter gen-l10n`. Any Malayalam or Sanskrit wording I am unsure of is flagged for review
  in the change log.

**Tests**

- `test/utils/screen_protection_test.dart`: on and off calls on Android; no calls on desktop.
- `test/providers/`: default is on, the choice is saved and read back, and it is not saved if the
  plugin call fails.
- Widget test: the switch shows on Android and is hidden on desktop; turning it off shows the
  warning, and cancelling keeps protection on.

### Decision to record: guideline §15.2

Engineering standard §15.2 says screen capture protection MUST be on for every screen that shows
sensitive data. A user-controlled off switch goes beyond that rule. The app still meets it by
default, and only the user's own choice, after a warning, turns it off. This is recorded as a
deliberate choice in `docs/security.md` (§1.1, §10 and §12 as needed). The submodule is not
edited.

## How it will be checked

- `dart format`, `flutter analyze` and `flutter test` run locally (the same steps as CI).
- CI itself only runs after the work is committed and pushed. Many needed files are still
  uncommitted (for example `lib/l10n/`, `fonts/`), so they must all be in that commit or CI will
  fail. Nothing is committed or pushed as part of this plan.
- The real screenshot block can only be confirmed on a phone, which is the planned next step.
