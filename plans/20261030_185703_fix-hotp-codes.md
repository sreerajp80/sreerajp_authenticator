# Fix HOTP codes

**Status:** completed

Bug found during Part 5d (`plans/20261030_072311_localization-part-5d-features-help.md`). Master
plan: `plans/20261029_183929_adopt-updated-guidelines.md`.

**Security impact:** small. It touches storage only to save the HOTP counter, which already sits in
the `accounts` table and is not a secret. The secret handling, permissions and network use do not
change. A code is never shown before its counter is saved, so a code cannot be used twice by
accident.

## What the issue is

An HOTP code depends on a counter, not on the time. The app gets this wrong:

- `lib/widgets/account_tile.dart` always calls `OTPService.generateTOTP`. An HOTP account therefore
  shows a **time-based code that the service will reject**, with a countdown ring that means nothing.
- `OTPService.generateHOTP` is correct and passes the RFC 4226 test values, but no screen calls it.
- Nothing ever moves the counter forward.
- `OTPService.generateOtpAuthUri` always writes `otpauth://totp/…`, so it would turn an HOTP account
  into a TOTP one. No screen calls it today, so users do not see this, but it is wrong.
- The QR parser accepts a negative counter. `counter=-1` gives a meaningless code.
- `docs/features.md` says HOTP accounts can be added by hand. The Add Account screen only makes
  TOTP accounts.

The help and features screens now say "HOTP is not supported yet" (Part 5d). This plan makes HOTP
work and corrects that text.

## How it will work

The stored counter means **the next unused value**. This matches the `counter=` value in an
`otpauth://hotp` QR code, so a new account's first code uses that value.

1. An HOTP tile has a "Next code" button instead of the countdown ring.
2. Before the first tap in a session, the tile shows the usual dashes, not a code.
3. A tap does these steps in order: make the code for counter C, **save C + 1**, then show the code.
   If the save fails, no code is shown.
4. The code stays on the tile until the app closes or locks. It does not change by itself.
5. Copy and show/hide work as they do for TOTP. Copying before the first tap gives a clear message
   ("Tap the next code button first").

Existing HOTP accounts need no migration, because their stored counters were never changed.

## Plan for the fix

### Service layer — `lib/services/otp_service.dart`, `lib/services/database_service.dart`
- New `OTPService.generateHOTPAsync(account)`, which decrypts the secret the same way as
  `generateTOTPAsync` and then uses the same code as `generateHOTP`.
- `generateOtpAuthUri`: HOTP accounts get `otpauth://hotp/…&counter=C` with no `period`.
- QR parser: an HOTP QR code with a negative counter is refused through the existing safe failure
  path (returns `null`).
- New `DatabaseService.setHotpCounter(id, expected, next)`: one parameterized `UPDATE` with
  `WHERE id = ? AND counter = ? AND LOWER(type) = 'hotp'`. The type check protects mOTP accounts,
  which keep their PIN in the same `counter` column. It returns the number of rows changed, so a
  second tap at the same moment cannot reuse a counter.

### Provider — `lib/providers/account_provider.dart`
- New `Future<OTPGenerationResult> nextHotpCode(Account account)`: makes the code, saves the counter,
  updates that account in the in-memory list, then calls `notifyListeners()`. It does not reload the
  whole list, so the tile keeps its state. It returns a failure when the save fails.

### Widgets — `lib/widgets/account_tile.dart`
- HOTP accounts skip the timers and `generateTOTP`.
- `TimerIndicator` is replaced by an `IconButton` with a localized tooltip (engineering standard
  §7.8). The button is disabled while a request runs and hidden in selection mode.
- The new code is shown straight away. The existing 28-second auto-hide still applies.
- TOTP, Steam, Blizzard, YubiKey and mOTP tiles do not change.

### Text (`lib/l10n/app_{en,ml,sa}.arb`, then `flutter gen-l10n`)
- New keys: `tooltipNextCode` ("Next code"), `descHotpTapForCode`
  ("Tap the next code button first."), `errorHotpNextFailed` ("Could not get the next code.").
- Changed in all three languages, to say HOTP works: `descFeatures10`, `descFeatures11`,
  `helpTime11`, `helpTime12`, `helpTime13`, `helpFaq09`.
- The help text also warns:
  - Each tap uses up one code.
  - A restored backup, or a copy on a second device, can hold an older counter. The service may then
    reject codes until you tap a few more times.

### Tests
- `test/services/otp_service_test.dart`: `generateHOTPAsync` gives the RFC 4226 values, the URI
  round trip keeps HOTP and its counter, a negative counter is refused.
- `test/services/database_service_test.dart`: `setHotpCounter` changes HOTP rows only, never an mOTP
  PIN, and a stale `expected` value changes nothing.
- `test/providers/account_provider_test.dart`: tapping through counters 0, 1, 2 gives the RFC values,
  the counter survives a reload, a failed save returns no code.
- New `test/widgets/account_tile_hotp_test.dart` in `en`, `ml`, `sa` on a narrow screen: dashes before
  the first tap, no countdown ring, a tap shows the code, copy before the first tap shows the message.

### Docs
- `docs/features.md`: HOTP row, account tile line, and the two manual-entry lines (HOTP is QR only).
- `README.md`, `docs/architecture.md`: check that their HOTP lines are still true.
- `docs/security.md`: one line on saving the counter before showing the code.
- Change log with the translations marked for review.

## Not in this plan

- Adding HOTP accounts by hand. They can be added by QR code only. This can be a later plan if you
  want it.
- Keeping counters in step between two devices. Sync and restore only add missing accounts, so an
  existing account keeps its own counter.

## Risks

- A code that was shown but never used moves the counter ahead of the service. This is normal for
  HOTP: services accept a small window of later counters. The size of that window depends on the
  service, so many unused taps could put an account out of step. The help text says each tap uses a
  code.
- I cannot test against a real HOTP service here. The RFC 4226 test values are the check.
